# Phase 2 — API Layer + File Scanner

Status: Active
Estimated: 2 days
Prerequisites: Phase 1 complete

## Goal

Expose all CRUD operations via FastAPI endpoints and implement real audio
metadata extraction with `mutagen`. By the end of this phase, the backend
can be fully driven via `curl` — scan a music folder, get songs, update
notes, create sets.

## Context

The frontend's `storage.ts` has 33 methods. Each needs a corresponding API
endpoint. The API must return JSON that matches the TS interfaces exactly
(camelCase where TS expects camelCase).

## Tasks

| Method | Path | Description | Request Body | Response |
|---|---|---|---|---|
| GET | `/api/songs` | List all songs | — | `Song[]` |
| GET | `/api/songs/{id}` | Get one song | — | `Song` |

### 2.8 — Library scan endpoint (`backend/api/library.py`)

```
POST /api/library/scan
Body: { "root_path": "/home/tim/Music" }
Response: {
  "total": 247,
  "added": 180,
  "skipped": 67,
  "errors": [...]
}
```

Implementation:
1. Validate `root_path` exists and is a directory
2. Walk directory tree recursively (using `pathlib.Path.rglob`)
3. Filter to supported audio extensions (from `config.py`)
4. For each file:
   a. Extract metadata via `mutagen` (see 2.9)
   b. Derive `root_folder` from parent folder name relative to `root_path`
   c. Check if song already exists (by `file_path` or artist+title)
   d. If new: create song record, add to store
   e. If exists: skip (idempotent — never overwrite user notes/tags/ratings)
5. Return summary stats

**Synchronous for MVP.** 1,000 files with mutagen takes ~10–30 seconds.
The frontend shows a spinner. Background jobs with polling come later if
needed.


**BPM and key are often missing** from file metadata. If not present:
- `bpm`: `None` (user enters manually or future AI detection)
- `musical_key`: `None` (same)
- `title`: fall back to filename stem
- `artist`: fall back to "Unknown Artist"

**Artwork extraction**: if embedded artwork exists, extract to a data URI
(`data:image/jpeg;base64,...`) or save to `~/.klangkurator/artwork/` and
store the path. For MVP, skip artwork — it's a nice-to-have, not critical.

### 2.11 — Root folder persistence

```
GET /api/library/root
Response: { "root_path": "/home/tim/Music" }

PUT /api/library/root
Body: { "root_path": "/home/tim/Music" }
Response: { "root_path": "/home/tim/Music" }
```

The root path is stored in `~/.klangkurator/config.json` (or in
`library.json` under a `_config` key).

### 2.12 — Error handling

- 404 for missing song/tag/block/set by ID
- 422 for invalid request bodies (Pydantic validation — automatic)
- 400 for scan errors (invalid path, permission denied)
- All errors return `{ "detail": "message" }` (FastAPI default)

## Deliverable

```bash
# Scan a music folder
curl -X POST http://localhost:8000/api/library/scan \
  -H "Content-Type: application/json" \
  -d '{"root_path": "/home/tim/Music"}'
# → {"total": 247, "added": 180, "skipped": 67, "errors": []}

# List songs
curl http://localhost:8000/api/songs | jq '.[0].title'
# → "Beyond Beliefs"

# Update a song's notes
curl -X PUT http://localhost:8000/api/songs/{id} \
  -H "Content-Type: application/json" \
  -d '{"drum_notes": "Soft 4/4, organic percussion"}'

# List crates
curl http://localhost:8000/api/library/crates
# → [{"name": "Melodic Techno", "track_count": 42}, ...]
```

## Key Decisions

- **REST conventions**: standard CRUD with `/api/{resource}` and
  `/api/{resource}/{id}`. No GraphQL, no custom action endpoints (except
  `/api/library/scan` which is an action, not a resource).
- **Synchronous scan**: no background jobs for MVP. If the scan takes 30s,
  the frontend shows a spinner. The response includes all stats.
- **Artwork deferred**: no artwork extraction in MVP. `artwork_url` is
  always `None`. Artwork is a polish item.
- **No pagination**: return all songs in one response. 1,000–5,000 songs
  is ~5–50 MB JSON — fine for a local app. Pagination can be added later
  if the frontend lags.
